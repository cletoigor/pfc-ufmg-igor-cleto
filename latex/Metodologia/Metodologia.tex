\chapter{Metodologia}

Neste capítulo, são detalhadas as etapas metodológicas adotadas no desenvolvimento do sistema inteligente para monitoramento e controle estatístico de processo (CEP) para o monitoramento do consumo de energia residencial. A abordagem foi projetada para atender aos objetivos do projeto, combinando análise técnica, desenvolvimento de soluções e validação experimental. Os procedimentos descritos têm como objetivo garantir a reprodução, escalabilidade e eficácia do sistema proposto, contribuindo para o avanço na área de automação e eficiência energética.

\section{Pesquisa e Análise de Tecnologias Existentes}
\label{sec:pesquisa_tecnologias}

A fase inicial do projeto focou na identificação e análise de tecnologias para monitoramento de consumo energético residencial, consultando diversas fontes e comparando soluções desde hardware customizado até dispositivos comerciais. O objetivo era balancear capacidade técnica, esforço de desenvolvimento, custo e alinhamento com os objetivos do PFC, utilizando critérios técnicos e práticos.

Considerou-se as seguintes abordagens:

\begin{enumerate}
    \item \textbf{Desenvolvimento de Hardware Customizado}: Implicaria criar um novo dispositivo de medição, com microcontroladores (e.g., ESP32, Arduino) e sensores de corrente/tensão.
    \begin{itemize}
        \item \textit{Vantagens}: Máxima flexibilidade no design, componentes, amostragem e formato de dados, proporcionando aprendizado em medição de energia e sistemas embarcados.
        \item \textit{Desvantagens}: Exigiria conhecimento especializado em eletrônica, design de PCB, calibração e programação embarcada. Custos de prototipagem e tempo de desenvolvimento seriam elevados, além de preocupações com segurança elétrica. Esta opção foi descartada devido ao foco do projeto em software e ao tempo e custo envolvidos.
    \end{itemize}

    \item \textbf{Tomadas Inteligentes Comerciais com Protocolos Diversos}: Utilização de smart plugs comerciais, que já medem energia e são de fácil instalação, diferenciando-se pelo protocolo de comunicação.
    \begin{itemize}
        \item \textit{Protocolo Wi-Fi (como a linha Tuya)}: Conectam-se diretamente ao roteador Wi-Fi, sem necessidade de hub. A configuração é simples via app móvel, e a comunicação com a nuvem permite controle remoto e acesso a dados. A disponibilidade de uma API de nuvem é crucial.
        \item \textit{Protocolos de Baixo Consumo e Redes Mesh (e.g., Zigbee, Z-Wave)}: Otimizados para baixo consumo e redes mesh, aumentando alcance e confiabilidade. Requerem um hub específico, adicionando custo e complexidade. Foram considerados menos diretos para os objetivos do projeto que priorizavam uma API de nuvem acessível sem hardware intermediário adicional.
        \item \textit{Bluetooth Low Energy (BLE)}: Baixo consumo energético, mas com alcance limitado e geralmente necessitando de um gateway para monitoramento contínuo, tornando-se menos prático para este projeto.
    \end{itemize}
\end{enumerate}

A avaliação baseou-se nos seguintes critérios:

\begin{itemize}
    \item \textbf{Compatibilidade com infraestruturas residenciais convencionais}: Prioridade para soluções \textit{plug and play} que minimizam modificações.
    \item \textbf{Eficiência técnica}: Precisão, resolução, confiabilidade das medições e frequência de coleta.
    \item \textbf{Interoperabilidade}: Capacidade de integração com outros sistemas.
    \item \textbf{Custo-benefício}: Custo total da solução em relação aos benefícios.
    \item \textbf{Disponibilidade de API e Ecossistema de Desenvolvimento}: Acesso programático aos dados e controle dos dispositivos.
\end{itemize}

Após ponderar esses critérios, a linha de tomadas inteligentes \textit{Tuya Smart Wi-Fi} foi selecionada. A decisão fundamentou-se no baixo custo, facilidade de instalação e configuração (\textit{plug and play} via Wi-Fi), acesso a uma API de nuvem (\textit{Tuya Cloud API}) para extração de dados e controle, e modularidade. Dado o foco do projeto em integrações de software e análise de dados, uma solução comercial com API robusta como a da Tuya mostrou-se estratégica, representando o melhor compromisso para a prototipagem rápida de um sistema funcional alinhado aos objetivos deste PFC.

\subsection{Seleção de Ferramentas de Software e Plataformas de Desenvolvimento}
\label{sec:selecao_software}

Além da escolha do hardware de monitoramento, a seleção das ferramentas de software e plataformas de desenvolvimento foi crucial para a arquitetura do sistema de coleta, processamento, análise e visualização de dados, bem como para a orquestração das tarefas automatizadas. As decisões foram pautadas pela adequação aos requisitos do projeto, facilidade de integração, robustez e o ecossistema de suporte disponível.

\subsubsection{Linguagem de Programação: Python}
Python foi escolhido como linguagem principal devido ao seu vasto ecossistema de bibliotecas para ciência de dados e interação com APIs (e.g., Pandas, \texttt{tuya-connector-python}), sintaxe clara que acelera o desenvolvimento, comunidade ativa e facilidade de integração com as demais ferramentas do projeto. Alternativas como Node.js, Java ou C\# foram consideradas, mas Python ofereceu o melhor equilíbrio entre capacidade analítica, velocidade de desenvolvimento e bibliotecas específicas para as tarefas centrais deste PFC.

\subsubsection{Biblioteca Pandas e Estrutura DataFrame}
\label{subsubsec:pandas_dataframe}
A biblioteca Pandas, com sua estrutura central DataFrame, foi fundamental para a manipulação e análise de dados neste projeto. Os DataFrames, estruturas tabulares bidimensionais, foram extensivamente utilizados para carregar o mapeamento de dispositivos, auxiliar no pré-processamento dos dados da API Tuya (detalhado na Seção \ref{subsubsec:pipeline_dagster} sobre a pipeline Dagster) e na preparação dos dados para visualização na interface Streamlit (Seção \ref{subsec:desenvolvimento_streamlit}). Suas funcionalidades de leitura, escrita, filtragem, agrupamento e transformação de dados foram essenciais.

\subsubsection{Plataforma de Interface de Usuário: Streamlit}
Streamlit foi escolhido para a UI devido à sua capacidade de desenvolvimento rápido de aplicações web interativas usando apenas Python, ideal para prototipagem e foco na análise de dados. Sua simplicidade na criação de widgets e renderização de gráficos a partir de DataFrames Pandas, juntamente com ferramentas como \texttt{@st.cache\_data} e \texttt{st.session\_state}, permitiu a criação de uma interface rica e responsiva com esforço mínimo de frontend. Alternativas como Dash (Plotly) ou soluções full-stack tradicionais (Flask/Django + React/Vue/Angular) foram consideradas, mas Streamlit ofereceu a maior eficiência para os objetivos e restrições deste PFC.

Para otimizar o carregamento e processamento de dados analíticos pela aplicação Streamlit, o formato Parquet foi escolhido para a camada de dados de staging (\texttt{app/data/staging/}). Suas vantagens incluem armazenamento colunar eficiente para consultas analíticas (reduzindo I/O), compressão eficaz por coluna, desempenho superior em operações OLAP devido ao layout colunar e técnicas como \textit{predicate pushdown}, suporte a tipos de dados complexos, evolução de esquema e ampla integração com o ecossistema de dados (incluindo DuckDB e Pandas). Em comparação, formatos como CSV são ineficientes para grandes volumes analíticos, e JSON, embora bom para dados semiestruturados, é menos performático para consultas tabulares. A escolha pelo Parquet foi, portanto, estratégica para o desempenho das análises e a eficiência do armazenamento, beneficiando a responsividade da aplicação Streamlit.

\subsubsection{Plataforma de Orquestração de Dados: Dagster}
Dagster foi escolhido para orquestrar os fluxos de dados (coleta da API Tuya, processamento, agendamento de cenas) devido à sua abordagem centrada em ativos de dados (\textit{Software-defined Assets}), desenvolvimento nativo em Python, excelente observabilidade via interface Dagit, gerenciamento de configuração com \texttt{Resources} (e.g., \texttt{TuyaCredentials}, \texttt{DuckDBResource}), agendamento robusto, testabilidade e facilidade de desenvolvimento local. Alternativas como Apache Airflow (mais complexo para o escopo do PFC), Prefect (similar, mas a escolha recaiu sobre Dagster) e scripts agendados via cron (carentes de funcionalidades avançadas de pipeline) foram consideradas. Dagster ofereceu o melhor equilíbrio entre modernidade, facilidade de uso, robustez e observabilidade para este projeto.

\subsubsection{Banco de Dados Analítico Embutido: DuckDB}
\label{subsubsec:selecao_duckdb}
DuckDB foi escolhido para o processamento analítico dos dados dos sensores na transição da camada bruta para a de preparação (staging). Este sistema de gerenciamento de banco de dados analítico (OLAP) embutido destaca-se pelo alto desempenho em cargas analíticas, operação in-process (eliminando a necessidade de servidor), integração profunda com Python/Pandas, capacidade de consultar diretamente arquivos Parquet/JSON, e sintaxe SQL completa. Alternativas como SQLite (mais OLTP), manipulação exclusiva com Pandas (potencialmente menos performático para transformações complexas ou grandes datasets) e bancos de dados baseados em servidor (e.g., PostgreSQL, MySQL, com maior overhead de infraestrutura) foram consideradas. DuckDB ofereceu o melhor equilíbrio para as necessidades do projeto, sendo utilizado como \texttt{DuckDBResource} no Dagster para transformações na camada de staging (Seção \ref{subsubsec:pipeline_dagster}).

\section{Desenvolvimento do Protótipo}
\label{sec:desenvolvimento_prototipo}
Com as tecnologias e ferramentas selecionadas, iniciou-se o desenvolvimento do protótipo funcional, integrando hardware e software para monitoramento energético, aplicação de CEP e interação via interface intuitiva. Esta fase visou materializar a arquitetura planejada em um sistema operacional eficaz.

\subsection{Seleção e Configuração de Sensores}
\label{subsec:configuracao_sensores}
Adquiriu-se um conjunto inicial de cinco tomadas inteligentes \textit{Tuya Smart Wi-Fi}, selecionadas pelo suporte à medição de energia, capacidade de corrente compatível (10A/16A), formato físico adequado e compatibilidade com a API Tuya. Utilizaram-se modelos genéricos "Smart Plug Wi-Fi" (e.g., com chipset BL0937), capazes de reportar potência, corrente e tensão. A interpretação correta dos \textit{data points} (DPs) e seus fatores de escala é crucial.

Os dados de consumo são enviados à nuvem Tuya em intervalos de uma hora e ficam disponíveis via API por 7 dias, necessitando da pipeline Dagster (Seção \ref{subsubsec:pipeline_dagster}) para armazenamento persistente e histórico para análises de longo prazo e CEP. A granularidade horária foi considerada suficiente para os objetivos do projeto. O mapeamento entre Device ID e nomes descritivos foi registrado em \texttt{app/data/device\_mapping.json}, essencial para o enriquecimento semântico dos dados, conforme exemplo:
\begin{verbatim}
{
  "bfxxxxxxxxxxxxxxSMARTPLUGID1": { "name": "Geladeira", "default_code": "switch_1" }
}
\end{verbatim}
O campo \texttt{default\_code} indica o DP para controle de ligar/desligar.

\subsection{Arquitetura e Desenvolvimento do Software de Coleta, Processamento e Controle}
\label{subsec:arquitetura_software}
O software do sistema transforma dados brutos de energia em informações acionáveis e permite controle automatizado. O desenvolvimento focou em um backend robusto para coleta e processamento de dados, lógicas de controle de cenas e orquestração eficiente com Dagster. A comunicação com as tomadas Tuya utiliza a \textit{Tuya Cloud API} via conector \texttt{tuya-connector-python}, que lida com autenticação HMAC-SHA256 e chamadas HTTP. A arquitetura é modular e escalável, usando Python e Dagster.

\subsubsection{Implementação da Pipeline de Dados com Dagster}
\label{subsubsec:pipeline_dagster}
A pipeline de dados de consumo energético foi implementada com Dagster para gerenciar o fluxo desde a extração da API Tuya até o armazenamento otimizado. A implementação incluiu:
\begin{itemize}
    \item \textbf{Configuração de Recursos}: Definição de \texttt{TuyaCredentials} (para gerenciar credenciais da API Tuya e o caminho do mapeamento de dispositivos via variáveis de ambiente) e \texttt{DuckDBResource} (para interação com DuckDB em memória).
    \item \textbf{Definição de Ativos}:
    \begin{itemize}
        \item \texttt{raw\_tuya\_logs}: Extrai dados brutos da API Tuya usando \texttt{tuya-connector-python}, salvando-os como JSONs particionados por \texttt{device\_id} e data em \texttt{app/data/raw/}.
        \item \texttt{staging\_tuya\_logs}: Transforma os JSONs brutos em formato Parquet particionado por \texttt{event\_date} na camada \texttt{app/data/staging/}. Utiliza \texttt{DuckDBResource} para carregar, transformar (converter timestamps, juntar mapeamento de dispositivos via Pandas) e salvar os dados.
    \end{itemize}
    \item \textbf{Criação de Job e Agendamento}: Um job (\texttt{tuya\_processing\_job}) encapsula os ativos e suas dependências. Um agendamento (\texttt{hourly\_schedule}) executa este job a cada hora (\texttt{"0 * * * *"}), garantindo a atualização regular dos dados.
    \item \textbf{Configuração do Ambiente Dagster}: Criação dos arquivos \texttt{dagster.yaml} e \texttt{workspace.yaml} para definir a instância e o local do código da pipeline.
\end{itemize}
Esta arquitetura proporciona uma solução robusta e automatizada para ingestão e preparação dos dados de consumo.

\subsubsection{Implementação do Agendamento de Cenas com Dagster}
\label{subsubsec:agendamento_cenas_dagster}
A comunicação com a API Tuya utiliza mecanismos padrão como HMAC-SHA256 para autenticação, e interações RESTful via chamadas HTTP (GET, POST) para consulta e envio de comandos.

A automação da execução de cenas foi implementada com Dagster para centralizar a lógica, aproveitar o monitoramento e logging da plataforma, e integrar-se ao sistema de gerenciamento de dados. A implementação compreendeu:
\begin{itemize}
    \item \textbf{Recurso de API Tuya para Cenas (\texttt{tuya\_api\_resource})}: Encapsula credenciais da API Tuya e a instanciação do cliente \texttt{tuya-connector-python}, injetado como dependência na operação de cenas.
    \item \textbf{Operação (Op) \texttt{check\_and\_trigger\_scenes\_op}}: Núcleo da execução de cenas. Esta função Python:
    \begin{enumerate}
        \item Lê e valida definições de cena do arquivo JSON \texttt{app/data/scheduled\_scenes.json} (gerenciado pela UI Streamlit), que contém ID, nome, dispositivos, ações, horário, dias de ativação e status de recorrência.
        \item Compara o agendamento da cena com o momento atual, considerando o fuso horário.
        \item Gerencia a lógica de recorrência, marcando cenas de execução única como "executada" após o acionamento para evitar repetições.
        \item Envia comandos à API Tuya para os dispositivos da cena, se as condições forem satisfeitas, tratando erros de comunicação e logando os resultados.
        \item Registra logs detalhados de todas as ações via \texttt{context.log} do Dagster.
    \end{enumerate}
    \item \textbf{Job e Agendamento}: Um job (\texttt{scene\_scheduler\_job}) encapsula a \texttt{check\_and\_trigger\_scenes\_op}. Um agendamento (\texttt{scene\_execution\_schedule}) executa este job a cada minuto (\texttt{"* * * * *"}), garantindo a verificação frequente e execução pontual das cenas.
\end{itemize}
Esta integração ao Dagster assegura robustez, monitoramento e configurabilidade para o agendamento de cenas.

\subsection{Desenvolvimento da Interface de Usuário com Streamlit}
\label{subsec:desenvolvimento_streamlit}
A interface de usuário (frontend) foi desenvolvida com Streamlit, permitindo foco na lógica da aplicação e apresentação dos dados. A metodologia incluiu:
\begin{itemize}
    \item \textbf{Estruturação Multi-Página}: Navegação via barra lateral entre seções como "Resumo da Casa", "Detalhes por Dispositivo", "Análise Avançada", "Controle Individual" e "Gerenciamento de Cenas", com cada página modularizada.
    \item \textbf{Carregamento e Filtragem de Dados}: Funções em \texttt{app/streamlit/utils/data\_helpers.py} carregam dados Parquet da camada de staging, aplicando filtros de usuário e utilizando cache (\texttt{@st.cache\_data}) para otimizar o desempenho.
    \item \textbf{Visualização Interativa}: Gráficos (séries temporais, barras, histogramas) e métricas (\texttt{st.metric}) foram implementados usando as capacidades nativas do Streamlit, com interatividade via widgets (seletores de data, dispositivo, botões).
    \item \textbf{Funcionalidades de Controle}:
    \begin{itemize}
        \item \textit{Controle Individual}: Widgets \texttt{st.toggle} com "atualização otimista" via \texttt{st.session\_state} e \texttt{st.fragment} para acionar comandos à API Tuya (via \texttt{app/streamlit/utils/tuya\_api\_helpers.py}).

    \item \textbf{Modularização do Código}: Lógica refatorada em módulos auxiliares em \texttt{app/streamlit/utils/} (\texttt{data\_helpers.py}, \texttt{ui\_helpers.py}, \texttt{page\_functions.py}, \texttt{tuya\_api\_helpers.py}).
    \item \textbf{Estilização Customizada}: Uso de CSS externo (\texttt{app/streamlit/style.css}) para melhorar a aparência visual.
\end{itemize}
Esta abordagem resultou em uma aplicação web funcional e interativa.

\section[Algoritmos de Processamento e Análise]{Implementação de Algoritmos de Processamento e Análise}
Para o tratamento dos dados, algoritmos específicos foram desenvolvidos.

\subsection{Pré-processamento dos Dados}
Os dados brutos das tomadas passaram por limpeza, transformação e normalização para garantir qualidade e consistência. O pré-processamento incluiu tratamento de leituras espúrias (valores anômalos removidos/ajustados), normalização (uniformidade de unidades, tratamento de dados faltantes com interpolação ou remoção) e enriquecimento (identificação do dispositivo, timestamp padronizado). O ativo \texttt{staging\_tuya\_logs} da pipeline Dagster realiza grande parte deste pré-processamento automaticamente, convertendo tipos de dados, enriquecendo com mapeamento de dispositivos de \texttt{app/data/device\_mapping.json}, e estruturando os dados em Parquet particionado.

\subsection{Análise Estatística e Controle Estatístico de Processos (CEP)}
\label{subsec:analise_cep}
O Controle Estatístico de Processo (CEP) é uma metodologia estatística para monitorar e otimizar processos, visando reduzir sua variabilidade. Distingue-se entre variação por causas comuns (inerente ao processo sob controle) e por causas especiais (eventos esporádicos). Gráficos de controle, com linha central (CL) e limites superior (UCL) e inferior (LCL), ajudam a identificar essas variações.

Para detectar anomalias no consumo energético, utilizou-se o gráfico de Soma Acumulada (CUSUM), eficaz na identificação de pequenas mudanças persistentes na média do processo, pois incorpora informações de observações passadas. A implementação seguiu uma abordagem estruturada:

\begin{itemize}
    \item \textbf{Fase I: Estabelecimento dos Parâmetros de Controle (Linha de Base)}: Coletou-se um conjunto de $m$ observações históricas ($X_1, \ldots, X_m$) do consumo de cada dispositivo, representativas da operação normal. A média $\mu_0$ e o desvio padrão $\sigma_0$ foram estimados a partir destes dados (Equações \ref{eq:media_controle} e \ref{eq:desvio_padrao_controle}) e usados como referência para a Fase II.
    \begin{equation}
        \hat{\mu}_0 = \bar{X} = \frac{1}{m}\sum_{j=1}^{m} X_j
        \label{eq:media_controle}
    \end{equation}
    \begin{equation}
        \hat{\sigma}_0 = s = \sqrt{\frac{1}{m-1}\sum_{j=1}^{m} (X_j - \bar{X})^2}
        \label{eq:desvio_padrao_controle}
    \end{equation}

    \item \textbf{Fase II: Monitoramento com Gráficos CUSUM Tabulares}: Novas observações $X_i$ foram monitoradas usando duas estatísticas CUSUM unilaterais:
    \begin{itemize}
        \item CUSUM Superior ($S_{Hi}$), para detectar aumentos na média: $S_{Hi} = \max(0, X_i - (\mu_0 + K) + S_{H(i-1)})$, com $S_{H0} = 0$.
        \item CUSUM Inferior ($S_{Li}$), para detectar diminuições na média: $S_{Li} = \max(0, (\mu_0 - K) - X_i + S_{L(i-1)})$, com $S_{L0} = 0$.
    \end{itemize}
    O valor $K$ é um parâmetro de referência (folga).

    \item \textbf{Seleção dos Parâmetros CUSUM ($K, H$) e Regra de Sinalização}: A performance do CUSUM depende da escolha da folga $K$ (tipicamente $k \cdot \sigma_0$, com $k=0.5$) e do limite de decisão $H$ (tipicamente $h \cdot \sigma_0$, com $h \in [4,5]$). Estes afetam o Comprimento Médio de Corrida (ARL) entre falsos alarmes (ARL$_0$) e a detecção de mudanças reais (ARL$_1$). Para este projeto, $K$ e $H$ foram ajustados empiricamente para equilibrar a detecção de anomalias e alarmes espúrios. Um sinal de fora de controle ocorre se $S_{Hi} > H$ ou $S_{Li} > H$, indicando uma mudança persistente no consumo e acionando investigação.
\end{itemize}

\textbf{Implementação Prática e Visualização no Streamlit}: A análise CUSUM foi integrada à página "Análise Avançada" do Streamlit. O usuário seleciona dispositivo e período, e a aplicação exibe gráficos CUSUM ($S_{Hi}$, $S_{Li}$) com limites $H$, usando Plotly. Cruzamentos dos limites indicam pontos fora de controle, e "fault logs" listam desvios para diagnóstico. Parâmetros $K$ e $H$ foram definidos empiricamente. Esta análise foi complementada por estatísticas descritivas (médias, medianas, desvios padrão, histogramas, boxplots) para uma visão completa dos padrões de consumo.

\section{Validação em Ambiente Real}
O protótipo foi validado em ambiente residencial real para aferir aplicabilidade, eficácia e resposta em tempo real (ou quase real). A validação abrangeu:
\begin{itemize}
    \item \textbf{Desempenho de Sensores e Algoritmos}: Avaliou-se a precisão das medições das tomadas Tuya comparando-as com um medidor calibrado sob diversas cargas. A eficiência dos algoritmos CEP (CUSUM) na detecção de anomalias foi testada com eventos simulados, observando rapidez, precisão da sinalização e latência da pipeline Dagster e UI Streamlit.
    \item \textbf{Usabilidade e Responsividade da Interface Streamlit}: Usuários-teste avaliaram clareza, navegação e intuitividade das funcionalidades de visualização e controle, com feedback coletado por observação e questionários.
    \item \textbf{Robustez e Confiabilidade em Operação Contínua}: O sistema operou por semanas para monitorar estabilidade, resiliência a falhas (Wi-Fi, API Tuya) e capacidade de recuperação da pipeline Dagster e agendador de cenas, além da pontualidade na execução de cenas.
\end{itemize}
Resultados detalhados foram documentados, fundamentando melhorias para otimizar eficiência, confiabilidade e experiência do usuário.

\section{Considerações sobre Viabilidade e Impacto Acadêmico}
\label{sec:viabilidade_impacto}
Embora de escopo acadêmico, o protótipo funcional permite considerações sobre sua aplicação e relevância.
\begin{itemize}
    \item \textbf{Custos de Implementação}: A replicação residencial é viável devido ao baixo custo das tomadas \textit{Tuya Smart Wi-Fi} e ao uso de software open-source (Python, Dagster, Streamlit, etc.), exigindo apenas um computador pessoal. Os custos são compatíveis com projetos de conclusão de curso.
    \item \textbf{Benefícios ao Usuário e Relevância Acadêmica}:
    \begin{itemize}
        \item \textit{Conscientização e Economia}: A visualização detalhada do consumo por aparelho (via Streamlit) capacita o usuário a identificar "vilões" energéticos, promovendo mudanças comportamentais e economia.
        \item \textit{Otimização e Automação}: O agendamento de cenas reduz consumo desnecessário e aumenta o conforto.
        \item \textit{Manutenção Preditiva}: O CEP (CUSUM) pode detectar anomalias no consumo de eletrodomésticos, indicando problemas antes de falhas totais e permitindo manutenção preventiva.
        \item \textit{Validação de Medidas de Eficiência}: O sistema permite verificar o impacto real de ações de economia.
        \item \textit{Base para Estudos Acadêmicos}: Os dados e interações podem fundamentar pesquisas em consumo energético, Nudge Theory, forecasting e otimização.
    \end{itemize}
    O potencial para economia, gestão aprimorada e contribuições acadêmicas é claro.
    \item \textbf{Impactos Socioambientais (Perspectiva Acadêmica)}: O projeto fomenta a cultura de eficiência energética, contribui para a discussão sobre redução da pegada de carbono e empodera o consumidor com conhecimento.
\end{itemize}
Em resumo, o protótipo valida a arquitetura e algoritmos, ilustrando o potencial de tais sistemas para beneficiar usuários e promover o uso sustentável da energia.
